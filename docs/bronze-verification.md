# Legacy identity-verification implementation (Kinkord KYC phase 1)

> Member-facing product terminology is **Kinkord KYC**. The `bronze_*` schema, code and provider identifiers in this document are temporary technical compatibility names for the existing identity-and-liveness stage; they are not a tier and do not award full Kinkord KYC.

This is a gated identity-stage integration, not an automatic Kinkord KYC award from one provider result. The production path uses a published Didit live workflow. Smile ID can only act as a fallback when it is also configured for `live`; a sandbox provider is never eligible in the live flow. The member page is at `/settings/kyc`; `/settings/verification/bronze` redirects there for compatibility.

The public Kinkord KYC privacy notice is at `/privacy/kyc`; `/privacy/verification` redirects there for compatibility. It identifies Kinkord Limited as controller, Didit as the verification processor, the explicit-consent basis, automated decisions with human fallback, Nigerian data-subject rights, EU processing, and Kinkord's derived-record schedule. The consent version is `bronze-2026-09-19-profile-match-v2`. Before enabling profile matching, Kinkord's responsible officer must confirm the company/contact details, Didit retention settings, and the notice. It supplements rather than replaces a site-wide privacy policy.

## Provider setup

Didit primary (API server only): set `DIDIT_API_KEY`, `DIDIT_LIVE_WORKFLOW_ID` (published live workflow), `DIDIT_RETURN_URL`, `DIDIT_WEBHOOK_SECRET`, and `BRONZE_POLICY_URL` (approved biometric/ID privacy notice). The workflow must include government ID, liveness, face match, and Nigerian NIN/BVN registry validation where applicable. Register the public HTTPS `/webhooks/didit` endpoint in the Didit console for production. Localhost has no public webhook; the status endpoint also re-fetches Didit decisions while pending. Store the API key and webhook secret in server-side secrets, never in source or `NEXT_PUBLIC_*`. AWS expects `ARN_DIDIT_API_KEY` and `ARN_DIDIT_WEBHOOK_SECRET` pointing to Secrets Manager values.

### Legacy sandbox workflow tooling (not used by production)

Create a separate **sandbox application** in Didit's Business Console, then copy its application-specific key from **API & Webhooks** into the ignored `apps/api/.env` as `DIDIT_SANDBOX_API_KEY`. Do not reuse a live application's `DIDIT_API_KEY`: Didit blocks live database-validation workflows until the organization has completed its first top-up, while sandbox checks are simulated. The provisioning script deliberately reads only the sandbox key.

Run `node scripts/provision-didit-bronze-workflow.mjs dry-run` to inspect the payload, `node --env-file=apps/api/.env scripts/provision-didit-bronze-workflow.mjs inspect` to see existing sandbox workflows, and `node --env-file=apps/api/.env scripts/provision-didit-bronze-workflow.mjs create` to publish the sandbox workflow. It creates **Kinkord Bronze - Nigeria Test** with ID capture, an 18+ rule, `ACTIVE_3D` liveness, ID-to-selfie face match and `nga_national_id` NIMC validation. It checks for a workflow with the same name before creating one and reads the result back to verify the key settings. BVN is not required; it is a separate optional registry service.

This sandbox tooling is retained only for isolated provider-development work and is not part of the current release configuration. The active API uses `DIDIT_MODE=live`, `DIDIT_API_KEY`, and `DIDIT_LIVE_WORKFLOW_ID`; a missing live value fails closed. The KYC page remains gated until `BRONZE_POLICY_URL` points to Kinkord's approved public biometric/ID notice.

Didit returns a hosted verification URL. The API re-fetches the decision and requires matching session, workflow and user before deriving checks. A Didit-level approval alone never grants Bronze: all required feature checks and profile identity fields must pass. Missing Nigerian registry, DOB, gender, or country evidence fails closed. When `DIDIT_PROFILE_FACE_MATCH_ENABLED=true` and a new consent is accepted, the API loads the exact private avatar snapshot and Didit's authenticated liveness selfie into memory, submits them to Didit's standalone Face Match endpoint, and immediately discards both bytes. The comparison uses `save_api_request=false`, so it does not create a separate Didit session. Only derived result metadata is kept. Set a calibrated `DIDIT_PROFILE_FACE_MATCH_THRESHOLD` from 90 to 100; this implementation defaults to 90 and routes anything else to the reviewer queue. A persistent per-attempt claim prevents repeated paid comparison calls from concurrent webhook/status requests.

Smile fallback: configure `SMILE_ID_PARTNER_ID`, `SMILE_ID_API_KEY`, `SMILE_ID_ENVIRONMENT` (`sandbox` or `live`), `SMILE_ID_CALLBACK_URL` (public HTTPS `/webhooks/smile-id`), and `SMILE_ID_POLICY_URL`. Store the API key in the `kinkord/smile-id` AWS secret and pass its full ARN as `ARN_SMILE_ID_API_KEY` to the infrastructure deployment. Keep production disabled until both provider workflows and the callback URLs have been tested.

The API records consent only after an approved notice and at least one provider are configured. It issues a Didit hosted session (or a Smile hosted token on fallback) after a member accepts versioned consent, supplies DOB/gender/country and uploads a profile photo within 90 days. The provider handles government ID entry and live camera capture. Callbacks are authenticated, correlated to the reserved user/session, and re-fetched from the provider before deciding. Only derived check flags, references, consent timestamps, reviewer decisions, and audit metadata are kept in Postgres; raw ID numbers, documents, biometric media, and callback bodies are not stored.

## Bronze decision and manual review

An approved biometric action, a verified ID, and matching DOB/gender/country are required. A completed government-ID face comparison **does not** prove that the same face matches the Kinkord profile photo. The API separately compares the live liveness selfie to the exact avatar snapshot. Only an explicit, clear single-face profile comparison plus every other check awards `verified`; a low score, warning, missing/ambiguous face, unavailable media or disabled comparison enters `manual_review`. No profile image URL, selfie, raw ID, video, embeddings or provider callback is persisted or exposed.

Set `BRONZE_REVIEWER_EMAILS` to an exact comma-separated allowlist of staff accounts with two-factor authentication enabled. The staff UI is `/settings/verification/reviews`; unauthorised or non-2FA accounts receive no queue data. The UI uses GET `/verification/bronze/reviews` (open cases with provider session reference and a short-lived signed current-photo URL) and POST `/verification/bronze/reviews/:id/decision` with JSON `{ "decision": "approve" | "reject", "profileFaceMatches": true | false, "evidenceReference": "provider job / internal case reference", "reason": "review notes, at least ten characters" }`. Approval is refused unless every other derived check passed and the user's current avatar is still the avatar captured at attempt start. Reviewers must compare the actual provider liveness capture to that avatar using their authorized provider-portal access before setting `profileFaceMatches: true`. Access and decisions are logged server-side; decisions, reviewer IDs, reasons and evidence references are persisted. Do not place document numbers or raw biometric data in those text fields.

Three attempts are the maximum. Failed attempts 1 and 2 can retry; the third failure enters the review queue. Pending sessions expire after 24 hours and count as a failed attempt. A manual review never silently approves a missing check. A Bronze badge is emitted only when the status is `verified` and the currently displayed avatar key still matches the verified avatar snapshot.

## Before release

Confirm the privacy/retention notice and provider DPA, configure and document Didit's operational retention, confirm exact Nigerian registry and ID-sourced demographic fields from the published live workflow, exercise real signed callbacks and adverse/provisional cases, calibrate the profile-photo threshold with approved test data, and confirm the hosted camera flow across mobile and desktop browsers. Set a deletion job for closed Kinkord consent, attempt, callback-fingerprint and review audit records under the stated schedule. Provide an avatar-change re-verification/review workflow: the badge currently disappears if the approved avatar changes, but an already verified account cannot self-start a fresh attempt. Run DB migration `0009` in staging and test recovery before any production rollout.

## Local smoke test

1. Start local PostgreSQL and MinIO using `docker compose up -d postgres minio minio-init`, then run `corepack pnpm --filter api db:migrate` for migration `0008`.
2. For an authorised live pilot, fill the ignored `apps/api/.env` with `DIDIT_MODE=live`, the server-only `DIDIT_API_KEY`, a **published live** `DIDIT_LIVE_WORKFLOW_ID`, and the approved `BRONZE_POLICY_URL`. Use a public HTTPS `DIDIT_RETURN_URL` and register `https://<api-host>/webhooks/didit` with its matching webhook secret.
3. Run `corepack pnpm --filter api dev` and `corepack pnpm --filter web dev`. Sign in at `http://localhost:3000/login`, add DOB/gender/country and a recent avatar at `http://localhost:3000/profile/edit`, then open `http://localhost:3000/settings/verification/bronze`.
4. Set `DIDIT_PROFILE_FACE_MATCH_ENABLED=true` and `DIDIT_PROFILE_FACE_MATCH_THRESHOLD=90` only after reviewing the notice. Consent, start verification, complete the Didit hosted camera flow and return to the Bronze page. Refresh status. A fully passing provider decision and clear profile comparison should award Bronze; any uncertain result should enter manual review. Reviewers must have 2FA and be listed in `BRONZE_REVIEWER_EMAILS`.

Do not run live user IDs or biometrics through an unapproved notice or an unreviewed workflow. Use Didit's sandbox/test data until the DPA, retention schedule, and exact output mapping have been signed off.
